    Platform and Toolchain

    Current state: Node.js ≥24 <25 with npm ≥11 <12 · Ruby 3.4.5 with YJIT · Jekyll 4.4.1 · TypeScript in strict mode targeting ES2022 · ESLint 10 flat config with zero-warning enforcement · Prettier · Jest 30 · Playwright with axe-core. The workspace runs on native Linux today (including ARM); the WSL guidance in older pages remains usable on Windows hosts but is no longer the primary environment.

    Why: staying on current LTS lines (Node 22 → 24, Ruby 3.3.8 → 3.4.5), YJIT’s measurable build-time gains, and stricter typing (ES2020 → ES2022 strict) that catches errors the older config allowed.

    Updates these pages:

    • Getting Started — states Ruby 3.3.8+YJIT and Node.js 22.8+; the setup flow is still correct, only the version floors moved.
    • Welcome to MIJUG .NET Workspace — states TypeScript 5.5+/ES2020 and a WSL-first environment.
    • Testing Performance and Development Evolution — references Jest 29; the suite now runs Jest 30.

    Repository Layout and Versioning

    Current state: the Jekyll site source lives in jekyll-site/ at the repository root. The former root folder name was docs/, renamed in August 2026 — a breaking layout change that drove the major version bump to 15.0.0. The _docs collection (this documentation) and its /docs/... URLs are unchanged; only the source folder moved.

    Why: one word, three meanings — the root source folder (docs/), this documentation collection (_docs), and the public repository’s GitHub Pages serving folder (/docs) all collided in tooling, scripts, and conversation. The rename removed the ambiguity; roughly 70 files (scripts, configs, tests) were updated and verified in the same change.

    Updates these pages: any older page showing docs/ as the site source folder in a tree or command — notably Getting Started and Welcome to MIJUG .NET Workspace. Substitute jekyll-site/ when following along.

    Deployment: Local and Deliberate, Not CI-Driven

    Current state: publishing is a local, operator-driven flow — a deploy script builds the site with strict frontmatter checking and syncs the output into the public repository, where the final commit and push are a manual step. GitHub Actions deployment workflows exist but are intentionally disabled; CI runs checks, not releases. Guardrails (both tooling hooks and permission rules) prevent editing the public repository or the generated _site output directly.

    Why: a one-person operation values a deliberate publish gate over automation speed. Disabling CI deploys eliminated an entire class of surprise-publish and drift failures, and the guardrails make the safe path the only path.

    Updates these pages:

    • Welcome to MIJUG .NET Workspace — describes “Automated CI/CD with GitHub Actions” and an “Automated deployment” workflow arrow; both now describe the disabled path, not the real one.
    • Exploring the Limitations of Gitea and Ruby — the Actions-simulation experiments it documents are historical context for a pipeline that no longer deploys.

    Accessibility: WCAG 2.2 AA Is Canonical

    Current state: the workspace targets WCAG 2.2 Level AA everywhere — test suites, content rules, and component guidance. The automated accessibility suite currently runs 52 checks green via Playwright + axe-core, alongside contrast validation and a test-harness URL parameter for manual passes.

    Why: 2.2 is a superset of the 2.1 criteria older pages cite, and several of its additions (focus appearance, dragging alternatives, consistent help) directly serve this site’s 55+ audience. Standardizing on one target also ended the 2.1-here/2.2-there drift between documents.

    Updates these pages:

    • Accessibility Testing Configuration — mixes 2.1 and 2.2 references; read every “2.1 AA” as “2.2 AA” today.
    • Rouge Syntax Highlighter Demo and HTML rel Attribute Guide — cite 2.1 AA compliance; the highlighter and link guidance themselves are still current.

    Build, Test, and Quality Gates

    Current state: the npm script surface has grown to ~216 scripts, distilled into a small set of key commands: a full precheckin gate (format → lint → build → test → validate) before any push, a quick deploy-readiness check, fast smoke tests, and the accessibility suite. The unit suite stands at 126 tests; smoke and browser-compatibility E2E suites run in under a minute. Zero-warning linting is enforced, and the Prettier configuration is honored consistently by both the npm scripts and editor tooling (a subtle ignore-file mismatch was fixed in August 2026).

    Why: the older pages’ “70+ npm commands” grew threefold; without a distilled command map and a single all-in gate, the script surface itself became a source of errors. The evolution documented in the testing pages (unit-first, consolidated E2E) is still the strategy — it has simply compounded.

    Updates these pages: Welcome to MIJUG .NET Workspace (command count), Performance Optimization Guide and Testing Performance and Development Evolution (strategy current; specific timings and counts have shifted), Browser Compatibility Testing, Browser Compatibility Detection & Testing System, Browser Management for Testing, and Mermaid Test Runner (all operational and current in approach).

    Content Pipeline: CMS Plus Enforced Validation

    Current state: FrontMatter CMS remains the visual content-management layer, but frontmatter correctness is now enforced by automated validation hooks at edit time — required fields per collection, filename-date rules for posts, and YAML validity — because production builds run with strict frontmatter checking that would otherwise fail at deploy time. Content scaffolding follows a draft → preview → publish flow with a standardized author byline, and the tags/categories vocabularies are the source of truth for taxonomy.

    Why: strict frontmatter only applies to production configs, so an error could pass every dev build and still break a deploy — validation at edit time closes that gap at the moment the mistake is made.

    Updates these pages: FrontMatter CMS Usage (still accurate for the CMS itself; the validation layer on top is new), Tags and Categories System Guide and Liquid Tags Examples (current).

    Theme Structure: Self-Contained Layouts

    Current state: this site’s active layouts (default and its no-ads variant) are self-contained — they carry their own head and footer markup inline rather than composing head.html and footer.html includes. The long-unused include copies of those files were removed in August 2026 after verification that nothing referenced them. Recent additions to the include library: structured-data markup for local search (a LocalBusiness schema sourced from site config) and a reusable newsletter sign-up section; the footer now carries the business phone number and service area on every page.

    Why: the dead include copies were a trap — edits to them silently changed nothing, since the layouts never read them. Deleting them made the real structure honest. The schema, phone, and service-area additions serve local-search visibility for the consulting practice.

    Updates these pages: Jekyll Themes: Complete Usage Guide — its layout-inheritance example ({% include head.html %} in a shared default layout) describes the classic Jekyll pattern, which is exactly what this repository doesn’t do; read it as general Jekyll education, not a description of this site.

    AI-Assisted Engineering (New Since the Docs Were Written)

    Current state: the private workspace carries a consolidated AI-agent configuration — canonical instructions, always-on safety rules (deploy guardrails, secrets protection), edit-time hooks (the frontmatter validation above, auto-formatting, session context), specialized subagents, and a curated business knowledge base. Bulk extraction and summarization work is routed local-first to self-hosted models on the LAN, selected per task from a benchmark-validated routing table, with cloud models reviewing and synthesizing. Earlier generations of AI tooling configuration were reconciled into this single setup and retired.

    Why: three generations of assistant config had accumulated with duplicated, drifting guidance; one canonical source ended the drift. The local-first policy keeps bulk content work fast, private, and inexpensive, with quality control retained at the review tier.

    Updates these pages: none directly — this capability postdates the documentation set. It is the reason recent site content and documentation (this page included) carry consistent validation and provenance discipline.
