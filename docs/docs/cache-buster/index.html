    Cache Buster: Versioning the Site's CSS and JS

    Browsers keep copies of stylesheets and scripts so pages load faster. When the site changes one of those files, the file needs a new address, or visitors’ browsers keep using the old copy. MIJUG.net handles this with a ?v= value on each asset URL. This page covers the scripts that set and check those values, as they work in November 2026. For general caching strategies (version strings, file hashes, cache headers, CDNs), see Cache Management Strategies.

    How It Works

    Two scripts share the job:

    • scripts/cache-buster-manager.js writes the cache-buster values into the two production Jekyll configs, jekyll-site/_config_prod.yml and jekyll-site/_config_prod_enhanced.yml, before a build.
    • scripts/cache-manager.js checks the built site in jekyll-site/_site/ and reports any local stylesheet, script, or image URL that lacks a valid ?v= value.

    Templates turn the values into URLs through the cached-asset.html include. Only the production configs carry the values. Development builds (_config_dev.yml) have none, so they fall back to the build time and every dev build gets fresh URLs.

    The Values in the Production Configs

    Key Format How it is computed Where it is used
    cache_buster_js 64-character hex SHA3-256 over the source trees src/assets/js/es13/ and src/assets/js/consent/ ?v= on JavaScript loaded through cached-asset.html and on the consent script.
    cache_buster_css 64-character hex SHA3-256 over jekyll-site/assets/main.scss and every file directly inside jekyll-site/assets/css/ ?v= on every other asset type loaded through cached-asset.html: stylesheets, images, fonts, icons, the manifest, and plain links
    build_time 14 digits, YYYYMMDDHHMMSS, local time The time of the run that detected a change Only the session-information script in the About page layout
    cache_bust true or false Set by the script flags Only the About page layout. Asset URLs do not check it

    The two hash values come from file contents, so they change only when those sources change. A new build_time on its own does not give the CSS or JavaScript a new URL.

    In a template:

    {% include cached-asset.html type="css" path="/assets/main.css" %}
{% include cached-asset.html type="js" path="/assets/js/mijug-es13.min.js" module=true defer=true %}

    renders as (hashes shortened):

    <link rel="stylesheet" href="/assets/main.css?v=40dc4992...">
<script type="module" src="/assets/js/mijug-es13.min.js?v=ba147ed8..." defer crossorigin="anonymous"></script>

    If cache_buster_js or cache_buster_css is empty, cached-asset.html uses the build time instead. A separate include, cache-bust.html, versions the logos, favicons, and slide-deck stylesheets with an 8-digit date (the page’s last_modified_at, otherwise the build date) and writes the cache-version meta tag. The scripts do not manage that date.

    What Gives build_time a New Value

    A plain run hashes these directories and compares the result with the assetHash saved in .cache-buster-state.json:

    • jekyll-site/assets/
    • jekyll-site/_includes/
    • jekyll-site/_layouts/
    • jekyll-site/_sass/ (still on the watch list, but the directory no longer exists, so it adds nothing)

    Adding, removing, renaming, or editing any file under them counts as a change. The script also writes a new build_time when you pass --force, and when the state file is missing or unreadable. The state file is gitignored, so the first run on a fresh clone always writes a new one.

    In practice build_time changes on almost every npm run deploy:production. jekyll-site/assets/js/ holds the obfuscated bundles that the previous build wrote, and the obfuscator configs set no fixed seed, so each rebuild produces different bytes.

    The 2025 version of this page listed seven “trigger files” (main.scss, mermaid.min.js, and others). That list is still in the script as _CACHE_TRIGGER_FILES, but nothing reads it.

    Files the Script Writes

    File In git Contents
    jekyll-site/_config_prod.yml and jekyll-site/_config_prod_enhanced.yml Yes The cache_bust, build_time, cache_buster_js, and cache_buster_css lines
    .cache-buster-state.json No (gitignored) assetHash and timestamp from the last detected change
    .last-es13-src-hash and .last-css-asset-hash Yes The JavaScript and CSS hashes, kept as a record. No script reads them back

    Commands

    Writing the Values: cache-buster-manager.js

    These commands change the production configs. Review the result and commit it (see Deploying).

    npm script Direct flag What it does
    npm run cache:manage (none) Recomputes both hashes and writes them, sets cache_bust: true, and writes a new build_time only if the watched directories changed
    npm run cache:force-update --force The same, but always writes a new build_time
    npm run cache:disable --disable Sets cache_bust: false and empties build_time. Leaves both hashes and the state file alone, so asset URLs keep their ?v= values
    npm run cache:enable --enable-only Sets cache_bust: true and restores build_time from the state file. Does not recompute the hashes
    (none) --quiet Prints errors only
    (none) --debug Accepted, but the script has no debug messages, so it changes nothing

    If you pass more than one mode flag, --enable-only wins, then --disable, then --force. When --enable-only finds no saved timestamp, it writes a new one and saves a state file with an empty asset hash, so the next plain run writes another new build_time.

    Output after an asset change (captured 2026-11-25 from npm run build:all, which calls the same routine):

    ✅ SUCCESS: Enabled cache busting in _config_prod.yml with timestamp 20261125194224
✅ SUCCESS: Enabled cache busting in _config_prod_enhanced.yml with timestamp 20261125194224
✅ SUCCESS: Cache busting values updated due to asset changes

    With no asset change since the last run, the last line reads “No asset changes detected, keeping existing cache busting values” and build_time stays the same.

    No command prints the current values. Read them from the config:

    grep -E '^(cache_bust|build_time|cache_buster_(js|css)):' jekyll-site/_config_prod.yml

    Checking the Built Site: cache-manager.js

    This script needs a build first. It reads the HTML in jekyll-site/_site/, and for every <link rel="stylesheet">, <script src>, and <img src> with a local URL it checks for ?v= followed by an 8-digit date, a 14-digit timestamp, or a 64-character hex hash. It skips external URLs, inline SVG data URIs, anything inside <noscript>, and elements that carry a data-skip-cache-bust attribute. By default it checks only the category and tag archive pages; --all checks the whole site.

    npm script Runs
    npm run cache:verify --verify (category and tag pages)
    npm run cache:verify:all --verify --all
    npm run cache:verify:verbose --verify --verbose
    npm run cache:verify:debug --verify --debug
    npm run cache:status --verify --quiet
    npm run cache:check-page -- <path> --verify --page <path>
    npm run cache:fix:dry-run --fix --dry-run
    npm run cache:fix --fix
    npm run cache:fix:all --fix --all
    npm run cache:fix-page -- <path> --fix --page <path>
    npm run cache:check-and-fix --verify, then --fix if the check fails
    Flag Effect
    --verify Check only. This is the default: any run without --fix is a check
    --fix Appends ?v=<current timestamp> (or &v=) to each failing URL and rewrites that HTML file in jekyll-site/_site/
    --dry-run With --fix, lists the fixes without writing anything
    --all Checks the whole site instead of the category and tag pages
    --page <path> Checks one file. Give the HTML file itself, such as /index.html or /docs/cache-buster/index.html
    --quiet Prints nothing. The exit code is the only result
    --verbose Adds skip counts and lists the cache-related includes and which layouts use them
    --debug Everything in --verbose, plus an element snippet for each issue
    --continue-on-css-error Skips pages the HTML parser cannot read instead of stopping
    --no-exit-code Exits 0 even when issues are found
    --fix-specific Not listed in --help. Limits the run to files already flagged in the same run; that list starts empty, so the run checks nothing
    --help Prints usage

    The exit code is 1 when a check finds issues (unless --no-exit-code), when jekyll-site/_site/ is missing, or when a page cannot be parsed. Otherwise it is 0.

    --fix edits generated files only, and the next build replaces them. Treat it as a stopgap and fix the template, usually by loading the asset through cached-asset.html.

    npm run cache:verify:all checked 242 files and 1,013 resources on the same build, with no issues.

    npm run cache:status no longer prints a status summary. Apart from npm’s own npm notice run lines, it prints nothing, so read the exit code:

    npm run cache:status; echo "exit code: $?"

    0 means no issues. 1 means issues were found or there is no build. Use the grep command above to see the values themselves.

    Related Scripts

    npm run cache:validate (scripts/cache-validation.js) checks build-cache settings for Jekyll and TypeScript, not asset URLs. cache:optimize runs a full-site check and then a parallel build, cache:performance adds a performance check after that, and cache:force-rebuild cleans and rebuilds Jekyll. None of them changes the cache-buster values.

    Deploying

    npm run deploy:production (scripts/deploy-optimized.js) refreshes the values before anything is cleaned or built:

    1. It runs node scripts/cache-buster-manager.js with no flags, which updates both production configs and the state file.
    2. It rewrites .last-es13-src-hash with the output of scripts/hash-es13-src.js, which hashes src/assets/js/es13/ only. After a deploy, that file therefore no longer equals cache_buster_js, which also covers the consent sources.
    3. If either step fails, it logs the error and carries on with the values already in the configs.
    4. The production build then runs with _config.yml,_config_prod_enhanced.yml, so the new values end up in every page that ships.

    Plain npm run deploy (scripts/deploy.js) and npm run build:jekyll-prod skip the refresh. They use whatever values are already in the configs.

    Commit the Refreshed Values

    After a production deploy, the configs hold the values that are now live. Commit them so the repository matches the site. A later build:jekyll-prod or plain deploy then reproduces the same URLs.

    git status --short jekyll-site/_config_prod.yml jekyll-site/_config_prod_enhanced.yml .last-es13-src-hash .last-css-asset-hash
git add jekyll-site/_config_prod.yml jekyll-site/_config_prod_enhanced.yml .last-es13-src-hash .last-css-asset-hash
git commit -m "chore(deploy): refresh cache-buster values for the vX.Y.Z deploy"

    Troubleshooting

    A change does not show for visitors. View the page source on the live site and compare the ?v= on the stylesheet or script with the value in jekyll-site/_config_prod.yml. If the two match but the content is old, the changed file is probably outside the hashed set (for example jekyll-site/assets/fonts/inter.css), so its URL did not change. An edit to the hashed sources gives a new value on the next deploy:production.

    The state file is damaged or deleted. The script warns, treats it as empty, and writes a new build_time on the next run. That is the same result as cache:force-update, so no manual reset is needed.

    Check a fresh production build:

    npm run build:jekyll-prod
npm run cache:verify:all

    cache:check-page reports success but checked 0 resources. See the --page entry under Known Issues and pass the HTML file path.

    Known Issues

    • --page with a folder path reports success without checking anything. A path such as /about or /docs/cache-buster/ matches the folder before its index.html, fails with EISDIR, and still ends with “All resources have proper cache busting!” and exit code 0. A path that matches nothing also exits 0. Pass the HTML file path and confirm that “Resources checked” is above zero.
    • cache-manager.js --quiet hides errors too, although --help describes it as “errors and results only”.
    • Gaps in what is hashed. jekyll-site/_sass/ is still watched but no longer exists, and the CSS hash ignores stylesheets outside main.scss and the top level of jekyll-site/assets/css/.
