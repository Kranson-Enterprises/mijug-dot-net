    Accessibility Testing Configuration

    This project tests against WCAG 2.2 Level AA using @axe-core/playwright (axe-core 4.13) on top of the Playwright E2E suite, plus a static color-contrast checker for the site palette. Accessibility is a core value of MIJUG.net — the audience skews 55+ — so the goal is an inclusive experience, not minimal compliance. Automated checks catch a meaningful subset of issues; manual keyboard and assistive-technology review is still required for real conformance.

    Overview

    Accessibility testing has four moving parts:

    • tests/e2e/accessibility.spec.ts — the WCAG 2.2 responsive suite: homepage audits across Desktop, Tablet, and Mobile viewports, organized by the four WCAG principles.
    • tests/e2e/code-block-accessibility.spec.ts — verifies the accessible code-block behavior (ARIA roles, keyboard focus, copy buttons) added by the site’s runtime enhancements.
    • tests/e2e/utils/accessibility-helpers.ts — the shared engine: axe builder configuration, per-browser optimizations, and reusable checks (headings, landmarks, alt text, links, forms, keyboard, touch targets).
    • scripts/contrast-check.py — static WCAG contrast-ratio math on the site palette, independent of any browser.

    The runtime code under test lives in src/assets/js/es13/code-highlighter.ts (labels highlighted code blocks with a language-aware aria-label, makes them keyboard-focusable with tabindex="0", keeps native pre/code semantics, and adds accessible copy buttons) and src/assets/js/es13/accessibility-enhancements.ts (scrollable-region keyboard support and touch-target sizing).

    Where it runs in the gates

    • npm run quick:deploy-ready (the pre-deploy gate) reaches the accessibility suite through validate:complete → validate:accessibility. This is the path the deploy checklist exercises before every publish.
    • CI runs npm run test:a11y as a dedicated, blocking step after the E2E tests.
    • npm run precheckin does not run accessibility tests — its E2E scope is the browser-compatibility spec only. Run npm run validate:accessibility alongside it when your change touches templates, styles, or content.

    Test Suites

    1. WCAG 2.2 responsive suite — tests/e2e/accessibility.spec.ts

    Tagged @a11y and @a11y-wcag2.2. Audits the homepage across three viewports — Desktop 1280×720, Tablet 768×1024, Mobile 375×667 — with tests organized by WCAG principle:

    • Perceivable — 1.1.1 image alt text; 1.3.1 heading hierarchy, landmarks, and form-label association; 1.4.3 color contrast (axe color-contrast rule).
    • Operable — 2.1.1 keyboard navigation; 2.4.4 descriptive link purpose; touch-target measurement on mobile (see below).
    • Understandable — 3.1.1 lang attribute and document structure.
    • Robust — a full axe-core scan with the complete WCAG tag set (this test was historically labeled “4.1.1 Parsing”; that criterion was removed in WCAG 2.2, and the scan is really a full-ruleset sweep covering ARIA name/role/value and more).

    Mobile adds: a full-page axe scan, form-element labeling checks, viewport-meta/no-horizontal-scroll validation, and a 44×44 px touch-target measurement that logs findings without failing — 44×44 is the WCAG 2.5.5 (AAA) size kept as a house best practice. The enforced AA criterion is 2.5.8 (24×24), covered by the axe target-size rule below.

    2. Code-block accessibility — tests/e2e/code-block-accessibility.spec.ts

    Tagged @a11y and @a11y-wcag2.2, with a @a11y-code-blocks-all multi-page describe. By default it tests one documentation page; setting TEST_ALL_CODE_PAGES=true walks every documentation page known to contain code blocks (the CODE_PAGES list in the spec — extend it when a new code-bearing doc is added). It combines:

    • Rule-scoped axe scans on .highlighter-rouge blocks (aria-roles, aria-required-attr, aria-valid-attr).
    • Custom assertions: each highlighted block keeps its native pre/code semantics (no synthetic role), carries a code-describing aria-label and tabindex="0", actually receives keyboard focus, and its copy button is visible, labeled, focusable, and responds to Enter with “Copied” feedback.

    This suite’s axe scans stay rule-scoped for speed; code-block color contrast is covered by the site-wide sweep, which scans code blocks with the full ruleset (the dark Rouge palette’s comment and keyword colors were brought up to AA in August 2026).

    3. Browser-info accessibility — tests/e2e/browser-compatibility.spec.ts

    One test in the browser-compatibility suite audits the About page’s browser-session section with axe and asserts each info field is visible, non-empty, and properly labeled.

    4. Site-wide sweep (opt-in) — tests/e2e/site-wide-accessibility.spec.ts

    npm run test:a11y:site answers “is every page checked?” with a yes: it reads the generated sitemap.xml (kept complete by jekyll-sitemap; pagecrypt-protected trees are excluded there by config), then runs the shared WCAG builder unscoped on every listed page — so content outside the main landmarks is covered too. It is deliberately not part of the standard gates (it takes a few minutes); run it before deploys that touch layouts, includes, or styles, and after adding new page types. A page added to the site is picked up automatically via the sitemap — no test-file list to maintain.

    The shared engine — tests/e2e/utils/accessibility-helpers.ts

    All axe scans go through shared builders that:

    • request the tags wcag2a, wcag2aa, wcag21a/wcag21aa, wcag22a, wcag22aa — the WCAG 2.2 tags activate axe’s target-size rule (SC 2.5.8, 24×24 px minimum), which axe keeps off unless explicitly requested;
    • exclude non-content noise (tracking pixels, hidden inputs, the Wayback toolbar, decorative role="presentation" elements) and disable link-in-text-block per project link styling;
    • apply per-browser adjustments: Firefox excludes visually-hidden helpers and disables color-contrast-enhanced (AAA); WebKit excludes absolutely-positioned elements and disables target-size due to rendering-engine differences;
    • scope the main scans to the main, nav, header, and footer landmarks for speed (the mobile full-page scan is unscoped);
    • provide the reusable checks: checkHeadingHierarchy, checkLandmarks, checkImageAltText, checkLinkDescriptions, checkColorContrast, checkKeyboardNavigation, checkFormLabels, checkDocumentStructure, and per-browser touch-target configurations.

    Static Contrast Checking

    scripts/contrast-check.py (run via npm run validate:contrast) implements the WCAG relative-luminance and contrast-ratio formulas directly. It parses the palette variables straight from the SCSS source (jekyll-site/assets/main.scss, resolving one level of $aliases with Sass’s last-definition-wins semantics) and evaluates the site’s critical pairs — body text, secondary greys, the brand blues including the accessible link color — against the AA (4.5:1) and AAA (7:1) normal-text thresholds. It exits non-zero when any pair fails AA (or when the palette can’t be resolved), so validate:contrast and the gates above it fail loudly on a contrast regression. AAA results are informational. It also warns when the stylesheet redefines a variable with a different value, so drift between the variable blocks can’t hide.

    WCAG 2.2 Coverage Map

    How each relevant WCAG 2.2 Level A/AA success criterion is covered:

    Success criterion Level Coverage
    1.1.1 Non-text Content A Automated — dedicated alt-text test + axe ruleset
    1.3.1 Info and Relationships A Automated — headings, landmarks, form labels + axe ruleset
    1.4.3 Contrast (Minimum) AA Automated — axe color-contrast + static palette checker
    2.1.1 Keyboard / 2.1.2 No Keyboard Trap A Automated (tab-order walk, code-block focus) + manual review
    2.4.4 Link Purpose (In Context) A Automated — descriptive-link check
    2.4.11 Focus Not Obscured (Minimum) AA New in 2.2 — manual check (verify sticky header never covers focus)
    2.5.7 Dragging Movements AA New in 2.2 — not applicable (no drag interactions)
    2.5.8 Target Size (Minimum), 24×24 px AA New in 2.2 — automated via axe target-size (Chromium/Firefox); 44×44 house measurement logged on mobile
    3.1.1 Language of Page A Automated — lang attribute validation
    3.2.6 Consistent Help A New in 2.2 — manual check (contact/help links consistently placed)
    3.3.7 Redundant Entry A New in 2.2 — not applicable (no multi-step forms)
    3.3.8 Accessible Authentication (Min.) AA New in 2.2 — largely N/A; the workshop password prompt must keep allowing paste and password managers
    4.1.2 Name, Role, Value A Automated — axe ARIA rules + code-block ARIA assertions
    4.1.3 Status Messages AA Partial — copy-button “Copied” feedback tested; broader AT review manual
    4.1.1 Parsing — Removed in WCAG 2.2 (obsolete; no longer tested or claimed)

    WCAG Standards Status (August 2026)

    WCAG 2.2 remains the standard to build and test against. It became a W3C Recommendation on 5 October 2023 and received a minor editorial update on 12 December 2024 (no success-criteria changes), with editorial errata continuing through 2025. The October 2023 text is also published as ISO/IEC 40500:2025. Compared to 2.1, version 2.2 added nine success criteria (six at A/AA — see the coverage map above) and removed 4.1.1 Parsing.

    WCAG 3.0 is a working draft, not a target. The W3C published an updated Working Draft on 3 March 2026: former “outcomes” are now called “requirements” (174 of them), and the conformance model moves from A/AA/AAA to Bronze/Silver/Gold scoring, with Bronze roughly comparable to today’s 2.2 AA. The W3C describes it as an incomplete draft that will change substantially, expects no completed standard for several more years, and will not retire WCAG 2 until well after that. Practical posture for this project: keep targeting 2.2 AA, and revisit when WCAG 3.0 reaches Candidate Recommendation.

    Tooling note: axe-core currently automates exactly one WCAG 2.2-specific rule — target-size (SC 2.5.8) — and Deque has indicated the remaining 2.2 criteria are unlikely to be automated because they need human judgment. That is why the new-in-2.2 rows above lean on manual checks.

    Known Limitations

    Automated results are honest only with their scope attached:

    • The standard gate scans the homepage; full-site coverage is opt-in via npm run test:a11y:site (every sitemap page) and TEST_ALL_CODE_PAGES=true (code-block checks on every code-bearing doc).
    • The gate’s main scans are scoped to the main/nav/header/footer landmarks; content outside them is covered by the unscoped mobile scan and the site-wide sweep.
    • The standard gate (test:a11y) runs Chromium only; use test:a11y:fast against a running server for Firefox/WebKit. WebKit is skipped on Linux (rendering limitation) and has target-size disabled.
    • Firefox and WebKit color-contrast checks tolerate a small number of engine-specific false positives; Chromium enforces zero violations.
    • Automated testing is not conformance. Manual keyboard walks, zoom/reflow checks, and screen-reader testing (NVDA/VoiceOver) remain part of any real audit.

    Running the Tests

    # Standard gate (Chromium, serial, starts its own Jekyll server)
npm run test:a11y

# Debugging with a visible browser
npm run test:a11y:headed

# All browsers against an already-running server (npm run dev:jekyll first)
npm run test:a11y:fast

# Individual suites
npx playwright test --grep @a11y-wcag2.2 --project=chromium        # WCAG responsive suite
npx playwright test code-block-accessibility.spec.ts --project=chromium
TEST_ALL_CODE_PAGES=true npx playwright test code-block-accessibility.spec.ts --project=chromium

# Full-site sweep — every page in sitemap.xml, unscoped axe scan (a few minutes)
npm run test:a11y:site

# Contrast + everything
npm run validate:contrast
npm run validate:accessibility
npm run validate:wcag
